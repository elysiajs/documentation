> Welcome back~

After a year of development, Elysia 2 RC is finally here.

Elysia 2 is still named [DayDream](https://youtu.be/3qRd7Ok0NVY), but the development took a long time, and the improvements from beta to RC were big enough to justify calling it Elysia 2.1. We decided to name this release as well.

Elysia 2 RC is named after [またおいで (Please come again)](https://youtu.be/ezOrPwjaHZo) by South& to honor the improvements we've made.

We recommended reading the [beta release note](/blog/elysia-20) first, as this release builds upon it.

---

## Memory usage

First, Elysia 2 is about a better foundation.

We entirely rewrote Elysia to shift its focus from throughput alone to efficiency across all axes, starting with memory usage.

We invested in understanding the internal memory structures of JSC and V8 and how to optimize Elysia's memory usage.

![Static Route Memory usage](/blog/elysia-20-rc/mem-static-route.webp)
![Dynamic Route Memory usage](/blog/elysia-20-rc/mem-dynamic-route.webp)

This means each route should use less memory than before. Even after a load test, peak memory shouldn't increase as much and should stay close to its pre-test level.

![Return status Memory usage](/blog/elysia-20-rc/mem-return-status.webp)
![Set Headers Memory usage](/blog/elysia-20-rc/mem-set-headers.webp)

An actual codebase almost always uses `set.headers` and `status` on the response, so this improvement is relevant to real codebases.

![Inline Response Memory usage](/blog/elysia-20-rc/mem-inline-response.webp)
![Inline Guard Memory usage](/blog/elysia-20-rc/mem-inline-guard.webp)

This means that response schemas and guards use much less memory than before. This is relevant to a larger codebase rather than a "Hello World" test or benchmark.

You wouldn't notice these improvements in a small "Hello World" demo benchmark. They become relevant in a real codebase, especially as the number of routes grows.

## Deeper type inference

Previously, we optimized Elysia's types to be as fast as possible within TypeScript's limits, so we had to limit what Elysia could do to keep type-checking time reasonable.

But now that TypeScript 7 has been released with much faster inference, we can give Elysia 2 much deeper type inference while still being conscious of type-checking speed.

We have expanded type inference to cover more cases, especially in error handling.

![Elysia infer error from all possible type](/blog/elysia-20-rc/error-infer.webp)

Elysia can now statically infer all possible types from macros, lifecycle hooks, and inline hooks. Even error responses can be mapped or overridden and remain statically analyzable.

This makes it easy to identify all possible errors and makes Eden Treaty and OpenAPI type generation more useful, as they can now generate much more accurate types for error responses.

![OpenAPI type gen showing all possible error](/blog/elysia-20-rc/openapi.webp)

With OpenAPI type generation, you no longer have to manually annotate errors. It lists all possible errors that the route can throw and generates a proper OpenAPI spec for them.

This is somewhat similar to neverthrow and covers a lot of Effect.ts error handling, but with Elysia's ergonomics.

See [Error Handling](/patterns/error-handling) to learn how to structure your code to make Elysia infer errors.

## Reverting breaking changes to the lifecycle API

Previously, in the beta, we renamed the lifecycle API to remove the `on` prefix. But after a lot of feedback, and to make migrating to Elysia 2 smoother, we decided to revert the lifecycle API to the original `on` prefix.

Now Elysia 1 plugins should just work with Elysia 2 without any modifications.

![Error hook](/blog/elysia-20-rc/error-hook.webp)

However, the two-parameter `onError` hook still has one breaking change: `code` is now an `Error` instance. Most plugins should still work.

## Custom macro types

We have a rule to reduce explicit types as much as possible by making Elysia infer them for you. But sometimes, the cases are too limited, and giving you complete control is better than trying to infer the types for you.

With Elysia 2, you can now annotate and control macro types explicitly.

![Macro Type](/blog/elysia-20-rc/macro-type.webp)

This is less ergonomic than we want, but it gives you more control. Consider it an opt-in advanced feature for type wizards and plugin developers.

See [Macro Type Lambda](/patterns/macro#type-lambda) for how to use it.

## Eden Plugin

Along with macro types, we are now introducing Eden Plugin with an explicit type.

![Eden Plugin](/blog/elysia-20-rc/eden-plugin.webp)

This lets you control the plugin's type so you can add custom fields or create new extensions to Eden Treaty.

See [Eden Treaty Plugin](/eden/treaty/plugin/) for how to use it.

## Node.js improvements

Elysia is a Web Standard framework similar to Hono. This means Elysia should be able to run on any runtime that supports Web Standard APIs.

Because Node.js doesn't provide a Web Standard HTTP server out of the box, we have to provide a compatibility layer to make Elysia run on Node.js, similar to other frameworks like h3, Hono, Next.js, Nuxt, and Astro.

We are now using `srvx` and `crossws` on Node.js, which also form the foundation of `h3`.

This allows Elysia to maintain good performance and stability on Node.js while still supporting Web Standard APIs.

## Compression plugin

We have added an officially maintained compression plugin to Elysia 2. It is a simple plugin that compresses the response body using gzip or brotli.

```ts
import { compress } from '@elysia/compress'

new Elysia()
  .use(compress())
```

It will use Bun's fast path when possible and fall back to the runtime's native compression.

See [Compression Plugin](/plugins/compress/) for more details.

## Stability

Elysia 2 RC was supposed to be released about two months ago. But because we wanted to make sure the release was stable and smooth, we decided to delay it for intensive testing.

The number of test cases has tripled since the beta release and is around 10 times what it was in 1.4, with several performance, memory-usage, and type-inference gates to make sure Elysia doesn't regress in the future.

We developed Elysia 2 while integrating it with our internal servers to make sure it's ready for production.

We are quite confident that Elysia 2 RC is stable and ready for production.

What you will see in Elysia 2 is not better performance, but much lower memory usage and startup times.

We recommend starting new projects with Elysia 2 RC and planning to migrate existing projects to Elysia 2 RC. The migration should be relatively easy with the codemod we provide:

```bash
bunx @elysia/codemod@latest
```

You can create a new project with Elysia 2 RC using:

```bash
bun create elysia && bun add elysia@rc
```

We also update Elysiajs skills for LLM with a much better structure as well. We recommend updating your skills to the latest version with:
```
bunx skills add elysia@rc
```
