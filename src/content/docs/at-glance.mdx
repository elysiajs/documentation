Elysia is an ergonomic web framework for building backend servers. It's designed for simplicity and type safety, with a familiar API, extensive TypeScript support, and optimizations for Bun.

Let's start with a small server.

## TypeScript

Elysia is designed to help you write less TypeScript. It infers types from your routes so you can focus on business logic instead of repeating declarations.

<CodePlayground
    elysia={paramsDemo}
    alias={{ '/user/:id': '/user/123' }}
    mock={{ '/user/:id': { GET: '123' } }}
>

```ts
import { Elysia } from 'elysia'

new Elysia()
    .get('/user/:id', ({ params: { id } }) => id)
    .get('/user/abc', () => 'abc')
    .listen(3000)
```

</CodePlayground>

The `:id` segment becomes `params.id` both at runtime and in the handler's types, without a manual declaration. Its type is `string`.

TypeScript is recommended, but it isn't required to use Elysia. Type inference helps while you write code; use a schema when you also need runtime validation.

## Type integrity

Import `t` from Elysia to define a schema that validates values at runtime and provides their TypeScript types. That gives your input a single source of truth.

Let's change the path parameter from a string to a number:

```ts
import { Elysia, t } from 'elysia'

new Elysia()
    .get('/user/:id', {
        params: t.Object({
            id: t.Number()
        })
    }, ({ params: { id } }) => id)
    .listen(3000)
```

The schema comes before the handler in Elysia 2. A request to `/user/123` gives the handler the number `123`; `/user/abc` fails validation. Hover over `id` in your editor to see the inferred `number` type.

The same schema describes the runtime check and the handler's TypeScript input.

## Standard Schema

Elysia supports [Standard Schema](https://github.com/standard-schema/standard-schema), so you can use compatible versions of your preferred validation library.

The ecosystem includes Zod, Valibot, ArkType, Effect Schema, Yup, Joi integrations, and [other implementations](https://github.com/standard-schema/standard-schema). Check that the library or adapter you use implements the Standard Schema interface.

```ts
import { Elysia } from 'elysia'
import { z } from 'zod'
import * as v from 'valibot'

new Elysia()
    .get('/id/:id', {
        params: z.object({
            id: z.coerce.number()
        }),
        query: v.object({
            name: v.literal('Lilith')
        })
    }, ({ params: { id }, query: { name } }) => id)
    .listen(3000)
```

Here Zod converts the path parameter to a number, while Valibot requires `?name=Lilith`. Elysia infers the validated types from both schemas.

## OpenAPI

Elysia works with standards such as OpenAPI, WinterTC, and Standard Schema so you can connect it to tools you already use.

Add the [OpenAPI plugin](/plugins/openapi/) to generate API documentation from your routes and schemas:

```ts
import { Elysia, t } from 'elysia'
import { openapi } from '@elysia/openapi'

new Elysia()
    .use(openapi())
    .get('/user/:id', {
        params: t.Object({
            id: t.Number()
        })
    }, ({ params: { id } }) => id)
    .listen(3000)
```

The plugin provides a documentation page you can share with your team. Use a release compatible with Elysia 2; see the plugin reference for installation and configuration.

## OpenAPI Type Gen

Elysia also supports generating OpenAPI schemas from TypeScript types with `fromTypes()`:

```ts {6}
import { Elysia, t } from 'elysia'
import { openapi, fromTypes } from '@elysia/openapi'

export const app = new Elysia()
    .use(openapi({
        references: fromTypes()
    }))
    .get('/user/:id', {
        params: t.Object({
            id: t.Number()
        })
    }, ({ params: { id } }) => id)
    .listen(3000)
```

This brings a FastAPI-like approach to TypeScript: use your code's types as input to documentation generation instead of duplicating them in manual annotations. See [OpenAPI from types](/patterns/openapi/#openapi-from-types) for its setup and supported types.

## End-to-end type safety

Type safety doesn't stop at the server. Elysia's client library, **Eden**, lets your frontend use the server's types, in a workflow similar to tRPC.

Export the type of your server from `server.ts`, then import it in `client.ts`:

<FileCodeBlock>
<TabItem label="server.ts">

```ts
import { Elysia, t } from 'elysia'
import { openapi, fromTypes } from '@elysia/openapi'

export const app = new Elysia()
    .use(openapi({
        references: fromTypes()
    }))
    .get('/user/:id', {
        params: t.Object({
            id: t.Number()
        })
    }, ({ params: { id } }) => id)
    .listen(3000)

export type App = typeof app
```

</TabItem>
<TabItem label="client.ts">

```ts
import { treaty } from '@elysia/eden'
import type { App } from './server'

const app = treaty<App>('localhost:3000')

// Request /user/617
const { data } = await app.user({ id: 617 }).get()

console.log(data)
```

</TabItem>
</FileCodeBlock>

Eden uses the existing Elysia types without a separate client code-generation step. The client imports only the server's type, keeping server implementation code out of its bundle.

Elysia is here to help you build a confident backend, and everything you connect to it.

## Type soundness

Successful responses are only part of an API. Elysia can infer **all possible response types**, including errors, so your client can handle them safely.

```ts title="server.ts"
import { Elysia, t } from 'elysia'

const plugin = new Elysia()
    .macro({
        auth: {
            cookie: t.Cookie({
                session: t.String()
            }),
            beforeHandle({ cookie: { session }, status }) {
                if (session.value !== 'valid')
                    return status(401)
            }
        }
    })

const app = new Elysia()
    .use(plugin)
    .get('/user/:id', {
        auth: true,
        params: t.Object({
            id: t.Number()
        })
    }, ({ params: { id }, status }) => {
        if (Math.random() > 0.1)
            return status(420)

        return id
    })
    .listen(3000)

export type App = typeof app
```

Here, Elysia can return a `number` for a successful request but also infer `401` or `420` error in type-level so client can handle all three cases with type safety.

```ts title="client.ts"
import { treaty } from '@elysia/eden'
import type { App } from './server'

const app = treaty<App>('localhost:3000')

const { data, error } = await app.user({ id: 617 }).get()

if (error)
    console.log(error.status, error.value)
else
    console.log(data)
```

The client can handle the typed success and error results. See [Eden](/eden/) for the client API and [macros](/patterns/macro/) for reusable route behavior.

## Platform agnostic

Elysia is optimized for Bun's native features, but it isn't limited to Bun. Its [WinterTC-compatible](https://wintertc.org/) Request/Response interface makes other runtime integrations possible.

You can use Elysia with:

- Bun.
- [Node.js](/integrations/node/).
- [Deno](/integrations/deno/).
- [Cloudflare Workers](/integrations/cloudflare-worker/).
- [Vercel](/integrations/vercel/).
- [Expo](/integrations/expo/) API routes.
- [Next.js](/integrations/nextjs/) API routes.
- [Astro](/integrations/astro/) API routes.

Each integration describes its adapter and deployment setup. The integrations section has more supported environments.
