## Dependency

Elysia ประกอบขึ้นจากแอป Elysia ขนาดเล็กหลายตัวที่ทำงานแยกกันได้ คล้ายกับ microservice ที่สื่อสารกัน

เมื่อ instance หนึ่งต้องใช้ service ของอีก instance คุณ**ต้องประกาศ dependency อย่างชัดเจน**

```ts
import { Elysia, t } from 'elysia'

class Auth {
    getProfile() {
        return { name: 'Elysia User' }
    }
}

const auth = new Elysia()
    .decorate({
        auth: new Auth()
    })

const main = new Elysia()
    .use(auth)
    .get('/profile', ({ auth }) => auth.getProfile())
```

ถ้าไม่มี `.use(auth)` handler จะไม่รู้จัก `Auth` การลงทะเบียนไว้บน instance อื่นไม่ได้ทำให้ใช้งานที่นี่ได้

ด้านล่างนี้แสดงจังหวะที่ dependency ยังไม่มี แล้วกลายเป็นใช้งานได้ กดปุ่มแต่ละขั้นเพื่อดูทีละขั้นตอน

<DependencyStory client:visible={{ rootMargin: '200px' }} />

แนวคิดนี้คล้ายกับ **dependency injection** คือแต่ละ instance ประกาศว่าตัวเองต้องใช้อะไร การประกาศอย่างชัดเจนทำให้ติดตาม dependency ได้ง่ายและนำโมดูลกลับมาใช้ซ้ำได้ง่ายขึ้น

### Deduplication

hook ของปลั๊กอินที่ไม่มีชื่ออาจถูกลงทะเบียนซ้ำหลายครั้งเมื่อปลั๊กอินนั้นถูกใช้ร่วมกันในหลาย instance

ตั้ง `name` ที่ไม่ซ้ำให้ปลั๊กอิน เพื่อให้ Elysia ตัด lifecycle hook ที่ซ้ำออกได้

```ts
import { Elysia } from 'elysia'

const ip = new Elysia({ name: 'ip' })
    .derive('global', ({ server, request }) => ({
        ip: server?.requestIP(request)
    }))
    .get('/ip', ({ ip }) => ip)

const router1 = new Elysia()
    .use(ip)
    .get('/ip-1', ({ ip }) => ip)

const router2 = new Elysia()
    .use(ip)
    .get('/ip-2', ({ ip }) => ip)

const server = new Elysia()
    .use(router1)
    .use(router2)
```

`'global'` จะแชร์ hook ไปยังทุก instance ที่ใช้ปลั๊กอินนี้ ไม่ว่าจะใช้โดยตรงหรือผ่านปลั๊กอินอื่น ดู [scope](#scope) hook `ip` ที่แชร์กันจะทำงานเพียงครั้งเดียวต่อ request แม้ router ทั้งสองตัวจะใช้มัน ส่วน `requestIP` จะใช้ได้เมื่อ server adapter ที่รองรับส่ง `server` มาให้ ถ้าไม่มี `ip` จะเป็น `undefined`

ด้านล่างนี้คือตัวอย่างเดียวกันแบบเคลื่อนไหว ดู `ip` เข้าไปอยู่ใน router ทั้งสองตัว แล้วถูกลงทะเบียนเพียงครั้งเดียวเมื่อ `server` ใช้ router ทั้งคู่

<DeduplicationStory client:visible={{ rootMargin: '200px' }} />

สำหรับปลั๊กอินที่ตั้งค่าได้ ให้ใส่ตัวเลือกของมันเป็น `seed` การผสมกันของ `name` และ `seed` ใช้ระบุตัวตนของปลั๊กอิน การตั้งค่าที่เหมือนกันจะถูกตัดตัวซ้ำออก ส่วน seed ที่ต่างกันจะแยกจากกัน

```ts
import { Elysia } from 'elysia'

const version = (value = 1) => new Elysia({
    name: 'version',
    seed: value
})
    .get('/version', value)
```

การตั้งชื่อปลั๊กอินช่วยตัดการลงทะเบียนที่ซ้ำ แต่ไม่ได้หยุด factory ของปลั๊กอินไม่ให้ทำงานเมื่อคุณเรียกมัน งานที่ควรเกิดขึ้นครั้งเดียวจึงควรอยู่นอกการเรียก factory ที่เกิดซ้ำ

### Dependency แบบ global กับแบบระบุชัดเจน

dependency บางตัวเหมาะจะเป็นแบบ global ส่วนบางตัวควรประกาศในทุก instance ที่ใช้งาน

| ใช้ dependency แบบ global สำหรับ | ใช้ dependency แบบระบุชัดเจนสำหรับ |
| --- | --- |
| ปลั๊กอินที่ไม่ได้เพิ่ม type เช่น CORS, compression หรือ security header | ปลั๊กอินที่เพิ่ม type เช่น macro, state หรือ model |
| lifecycle hook ที่ควรมีผลทั่วทั้งแอป เช่น tracing หรือ logging | business logic ที่ handler ใช้งาน เช่น authentication หรือฐานข้อมูล |

ตัวอย่างแบบ global ได้แก่ เอกสาร OpenAPI, tracing ด้วย OpenTelemetry และ logging ส่วนตัวอย่างแบบระบุชัดเจน ได้แก่ store และ session, model ของ ORM หรือ ODM, service สำหรับ authentication และฐานข้อมูล รวมถึงโมดูลของฟีเจอร์อย่างแชตหรือการแจ้งเตือน

ถ้า dependency ของคุณไม่จำเป็นต้องเป็นแบบ global ให้เลือกแบบระบุชัดเจนไว้ก่อน

## Scope

lifecycle hook ของ Elysia ถูก **encapsulate** ไว้ใน instance ของตัวเอง hook ของปลั๊กอินจึงไม่มีผลกับ route ของ instance ที่ใช้ปลั๊กอินนั้นโดยอัตโนมัติ

<span id="descendant"></span>

ในตัวอย่างด้านล่าง `current.use(child)` ทำให้ `child` เป็น **descendant** ของ `current` ส่วนในทางกลับกัน `parent.use(current)` ทำให้ `parent` เป็น **parent** โดยตรงของมัน และ `main.use(parent)` ก็เพิ่ม parent อีกชั้นไว้ด้านบน

### ระดับของ scope

เลือกว่า hook จะมีผลไปไกลแค่ไหนด้วย argument ตัวแรกของ `onBeforeHandle` ได้แก่ `local`, `plugin` หรือ `global`

ทุกขั้นใช้ปลั๊กอิน tree ชุดเดียวกัน ต่างกันแค่ scope เท่านั้น hook จะ log ค่า `hi` โดยไม่คืนค่าอะไร ทุก route จึงยังคืน response `hi` จาก handler ของตัวเอง

## Config

เพื่อให้ปลั๊กอินนำกลับมาใช้ซ้ำได้ ให้ผู้ใช้ตั้งค่าส่วนที่ต้องเปลี่ยนได้เอง ฟังก์ชันหนึ่งรับตัวเลือกเข้ามาแล้วคืนค่าเป็น instance ของ Elysia ได้

```ts
import { Elysia } from 'elysia'

const version = (version = 1) => new Elysia()
    .get('/version', version)

const app = new Elysia()
    .use(version(1))
    .listen(3000)
```

ตัวอย่างนี้ `/version` จะคืนค่า `1` ถ้าส่งค่าอื่นเข้าไปก็จะได้ปลั๊กอินที่ตั้งค่าต่างออกไป

### Functional callback

ถ้าทำได้ ให้เลือกใช้ instance ใหม่ของปลั๊กอินไว้ก่อน เพราะ functional callback รับ instance หลักเข้ามาโดยตรง ทำให้เข้าใจเรื่อง encapsulation และ scope ได้ยากขึ้น

วิธีสร้างคือเขียนฟังก์ชันที่รับ Elysia เข้ามาแล้วคืนค่า instance ที่ขยายแล้ว

<CodePlayground elysia={callbackDemo}>

```ts
import { Elysia } from 'elysia'

const plugin = (app: Elysia) => app
    .state('counter', 0)
    .get('/plugin', () => 'Hi')

const app = new Elysia()
    .use(plugin)
    .get('/counter', ({ store: { counter } }) => counter)
    .listen(3000)
```

</CodePlayground>

callback นี้กำหนด property ลงบน instance หลักโดยตรง `/plugin` จะคืนค่า `Hi` และ `/counter` จะคืนค่า `0`

ใน Elysia 2 getter `app.store` ของ instance แบบเดิมถูกเอาออกแล้ว ให้ใช้ `store` จาก context ของ handler เพื่ออ่าน state

:::tip[เลือกรูปแบบที่อ่านง่ายกว่า]

คุณไม่จำเป็นต้องเลือกใช้ callback เพื่อประสิทธิภาพ instance ของ Elysia มีขนาดเบา และการใช้ instance แยกยังช่วยให้ TypeScript มีขอบเขตในการอนุมาน type ที่ชัดเจนกว่าด้วย

:::

## Guard

guard ใช้กำหนด hook และ schema ให้หลาย route พร้อมกัน ให้วาง route ที่ต้องการไว้ใน callback ของมัน

```ts
import { Elysia, t } from 'elysia'
import { signUp, signIn, isUserExists } from './auth'

new Elysia()
    .guard(
        {
            body: t.Object({
                username: t.String(),
                password: t.String()
            })
        },
        (app) => app
            .post('/sign-up', ({ body }) => signUp(body))
            .post('/sign-in', {
                beforeHandle: isUserExists
            }, ({ body }) => signIn(body))
    )
    .get('/', 'hi')
    .listen(3000)
```

body schema มีผลกับ `/sign-up` และ `/sign-in` แต่ไม่มีผลกับ `/` ส่วนฟังก์ชันที่ import เข้ามาคือ logic เกี่ยวกับบัญชีผู้ใช้ของแอปพลิเคชันคุณ

| Path | มีการตรวจสอบ body |
| --- | --- |
| `/sign-up` | ใช่ |
| `/sign-in` | ใช่ |
| `/` | ไม่ |

guard รับ schema และตัวเลือกของ hook ได้เหมือนกับ route ต่างกันตรงที่ guard จะใช้ค่าเหล่านั้นกับทุก route ใน callback

ตัวอย่างนี้ให้ผลเหมือนกับการใส่ตัวเลือกเหล่านั้นซ้ำในทุก route:

```ts
import { Elysia, t } from 'elysia'
import { signUp, signIn, isUserExists } from './auth'

new Elysia()
    .post('/sign-up', {
        body: t.Object({
            username: t.String(),
            password: t.String()
        })
    }, ({ body }) => signUp(body))
    .post('/sign-in', {
        beforeHandle: isUserExists,
        body: t.Object({
            username: t.String(),
            password: t.String()
        })
    }, ({ body }) => signIn(body))
    .get('/', 'hi')
    .listen(3000)
```

ใน Elysia 2 schema ของ route จะแทนที่ schema ที่รับมาจาก guard ในส่วนเดียวกันโดยค่าเริ่มต้น ถ้าต้องผ่านทั้งสอง schema ให้เพิ่ม `schema: 'merge'` ใน guard ดูเพิ่มเติมได้ที่ [validation](/essential/validation/#merge)

### Grouped guard

[group](/essential/route/#group) รับ argument ได้สามตัว ได้แก่ prefix, ตัวเลือกของ guard และ callback ของแอป

เริ่มจาก group และ guard ที่ซ้อนกัน:

```ts
import { Elysia, t } from 'elysia'

new Elysia()
    .group('/v1', (app) =>
        app.guard(
            { body: t.Literal('Rikuhachima Aru') },
            (app) => app.post('/student', ({ body }) => body)
        )
    )
    .listen(3000)
```

ย้ายตัวเลือกของ guard ไปเป็น argument ตัวที่สองของ group เพื่อให้ได้ผลลัพธ์เดียวกันโดยซ้อนกันน้อยลง:

```ts
import { Elysia, t } from 'elysia'

new Elysia()
    .group(
        '/v1',
        { body: t.Literal('Rikuhachima Aru') },
        (app) => app.post('/student', ({ body }) => body)
    )
    .listen(3000)
```

ทั้งสองแบบลงทะเบียน `POST /v1/student` เหมือนกัน body ที่เป็น JSON string `"Rikuhachima Aru"` จะผ่านการตรวจสอบและถูกคืนค่ากลับมาโดย handler

### Inline as

ใส่ string ของ scope ไว้ก่อน callback เพื่อแชร์ lifecycle hook ตัวเดียว

```ts
import { Elysia } from 'elysia'

const plugin = new Elysia()
    .derive('plugin', () => ({ hi: 'ok' }))
    .get('/child', ({ hi }) => hi)

const main = new Elysia()
    .use(plugin)
    .get('/parent', ({ hi }) => hi)
```

property `hi` ที่ derive มาใช้ได้ในทั้งสอง route รูปแบบนี้เปลี่ยนแค่ scope ของ hook ตัวนี้เท่านั้น

### Guard as

ใส่ string ของ scope ไว้ก่อนตัวเลือกของ guard เพื่อแชร์ hook และ schema หลายตัวไปพร้อมกัน

```ts
import { Elysia, t } from 'elysia'

const plugin = new Elysia()
    .guard('plugin', {
        response: t.String(),
        beforeHandle() {
            console.log('ok')
        }
    })
    .get('/child', 'ok')

const main = new Elysia()
    .use(plugin)
    .get('/parent', 'hello')
```

response schema และ hook มีผลกับทั้งสอง route สำหรับ property ที่ derive มาและต้องการ type ให้ใช้ `.derive('plugin', callback)` แทนการใส่ไว้ใน guard นี้

### Instance as

`.as()` ยกระดับ scope ของ hook และ schema ที่ลงทะเบียนไว้บน instance ปัจจุบันแล้ว

```ts
import { Elysia } from 'elysia'

const plugin = new Elysia()
    .derive(() => ({ hi: 'ok' }))
    .get('/child', ({ hi }) => hi)
    .as('plugin')

const main = new Elysia()
    .use(plugin)
    .get('/parent', ({ hi }) => hi)
```

scope แบบ `plugin` มีผลขึ้นไปได้แค่ parent เดียว ถ้าต้องการให้ไปต่ออีกชั้น ให้ยกระดับ instance ของ parent ด้วย

```ts
import { Elysia, t } from 'elysia'

const plugin = new Elysia()
    .guard({ response: t.String() })
    .onBeforeHandle(() => { console.log('called') })
    .get('/child', 'ok')
    .as('plugin')

const instance = new Elysia()
    .use(plugin)
    .get('/parent', 'still ok')
    .as('plugin')

const parent = new Elysia()
    .use(instance)
    .get('/grandparent', 'also ok')
```

ตอนนี้ response schema แบบ string มีผลไปถึง `/grandparent` แล้ว การคืนค่าเป็นตัวเลขจาก route ใดก็ตามในนี้ถือว่าผิด schema ซึ่ง TypeScript จะชี้ให้เห็น และ response validation ก็จะตรวจจับได้ตอน runtime

## Lazy load

โดยค่าเริ่มต้น โมดูลจะถูกโหลดทันที ปลั๊กอินแบบ synchronous จึงถูกลงทะเบียนก่อนเซิร์ฟเวอร์เริ่มทำงาน โมดูลที่ประมวลผลหนักหรือ blocking อาจทำให้เซิร์ฟเวอร์เริ่มช้าลง

ปลั๊กอินแบบ asynchronous จะลงทะเบียน route ของตัวเองเมื่อ promise ของมัน settle แล้ว `.listen()` และ `app.fetch` จะรอโมดูลที่ค้างอยู่ทั้งหมดก่อนเริ่มรับ request มีแค่ `app.handle()` เท่านั้นที่ทำงานก่อนได้

### Deferred module

deferred module คือปลั๊กอินแบบ async ตัวอย่างนี้จะรอรายการไฟล์ของคุณก่อนลงทะเบียน route:

```ts title="plugin.ts"
import { Elysia, file } from 'elysia'
import { loadAllFiles } from './files'

export const loadStatic = async (app: Elysia) => {
    const files = await loadAllFiles()

    for (const asset of files) {
        app.get(asset, file(asset))
    }

    return app
}
```

ในตัวอย่างนี้ `loadAllFiles` คืนค่าเป็น array ของ path ของ asset ในเครื่อง ซึ่งใช้เป็น path ของ route ได้ด้วย ในไฟล์หลักของคุณ:

```ts title="index.ts"
import { Elysia } from 'elysia'
import { loadStatic } from './plugin'

const app = new Elysia()
    .use(loadStatic)
    .listen(3000)
```

### Lazy load module

`import()` แบบ dynamic ใช้โหลดปลั๊กอินแบบ synchronous หรือ asynchronous แบบ lazy ได้ ให้ export ปลั๊กอินเป็น default export ของโมดูล:

```ts title="plugin.ts"
import { Elysia } from 'elysia'

export default new Elysia()
    .get('/plugin', 'Hi')
```

```ts title="index.ts"
import { Elysia } from 'elysia'

const app = new Elysia()
    .use(import('./plugin'))
    .listen(3000)
```

วิธีนี้มีประโยชน์เมื่อการโหลดตัวโมดูลเองใช้ทรัพยากรสูง `.listen()` จะรอ `app.modules` ให้เอง เซิร์ฟเวอร์จึงไม่มีทางเริ่มทำงานโดยที่ route ยังไม่ครบ คุณต้อง await `app.modules` เองก็ต่อเมื่อเรียก `app.handle()` โดยตรง เช่นในเทสต์

### การทดสอบ

ในเทสต์ ให้ await `app.modules` ก่อนส่ง request ไปยัง route ที่เป็น deferred หรือ lazy load

```ts
import { describe, expect, it } from 'bun:test'
import { Elysia } from 'elysia'

describe('Modules', () => {
    it('inline async', async () => {
        const app = new Elysia()
            .use(async (app) => app.get('/async', 'async'))

        await app.modules

        const response = await app.handle(
            new Request('http://localhost/async')
        )

        expect(await response.text()).toBe('async')
    })
})
```
