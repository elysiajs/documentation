<h1 id="_top">JIT "compiler"</h1>

Elysia ปรับการทำงานให้มีประสิทธิภาพ ทั้งการดึงฟีเจอร์ของ runtime มาใช้ และขั้นตอนจัดการ request ในแต่ละครั้ง เช่น ถ้า route อ่านแค่ path parameter ก็ไม่ต้องเสียเวลาไป parse query หรือ body ที่ไม่ได้ใช้

ตั้งแต่เปิดตัว [Elysia 0.4](/blog/elysia-04/) เมื่อวันที่ 30 มีนาคม 2023 Elysia ก็ใช้วิธีสร้าง JavaScript handler สำหรับจัดการ request ขึ้นมาใหม่โดยใช้ `new Function(...)` ซึ่งนี่ไม่ใช่คอมไพเลอร์แบบดั้งเดิมที่คอยแปลงภาษาหนึ่งไปเป็นอีกภาษา แต่เป็นการเจาะจงสร้างโค้ดขึ้นมาให้พอดีกับ handler, schema และ hook ของแต่ละ route โดยเฉพาะ เราถึงใส่เครื่องหมายคำพูดไว้ที่คำว่า "compiler"

ใน v2 โค้ดส่วนที่สร้าง handler จะอยู่ที่ `src/compile/handler/` (รวมถึง `jit.ts`) ถ้าเป็นบทความเก่าๆ จะพูดถึง `src/compose.ts` ส่วน Sucrose ก็ยังอยู่ที่ `src/sucrose.ts` เหมือนเดิม

ตามปกติ แต่ละ route จะคอมไพล์ตอนถูกเรียกใช้งานครั้งแรก และพอสร้างโค้ดเสร็จแล้ว ครั้งต่อไปก็จะนำ handler เดิมกลับมาใช้ซ้ำได้เลย ส่วน static response หรือ route ที่คอมไพล์ไว้ล่วงหน้า (precompiled) จะแยกไปใช้เส้นทางการทำงานอื่น ทำให้ไม่ใช่ทุก request หรือทุก route ที่ต้องผ่านขั้นตอนการวิเคราะห์แบบเดียวกัน

## การวิเคราะห์โค้ดแบบ static (Sucrose)

*Sucrose* เป็นชื่อเล่นของโมดูลวิเคราะห์โค้ด ที่คอยบอก compiler ว่า handler แต่ละตัวต้องการใช้ฟิลด์ไหนใน context บ้าง โดย Sucrose จะอ่านโค้ดของฟังก์ชันผ่าน `Function.toString()` แล้ววิเคราะห์ดูว่ามีการดึงค่าตัวไหนไปใช้ โดยไม่ได้รัน handler จริงๆ ขึ้นมาเพื่อดูว่าต้องการอะไร

ลองดู route นี้เป็นตัวอย่าง:

```ts
import { Elysia } from 'elysia'

const app = new Elysia()
    .patch('/user/:id', ({ params }) => ({ id: params.id }))
```

handler ตัวนี้อ่านแค่ `params` โดยไม่ได้แตะ `body`, `query` หรือ `headers` เลยแม้แต่น้อย Sucrose จะส่งข้อมูลตรงนี้ไปช่วยในการคอมไพล์ route ซึ่ง compiler ก็จะดู hook กับ schema ควบคู่ไปด้วย เช่น ถ้าเราใส่ schema สำหรับตรวจสอบ `body` เอาไว้ compiler ก็จะยังเตรียมข้อมูลส่วนนั้นให้ตามปกติ ถึงแม้ใน handler จะไม่ได้อ่าน `body` โดยตรงก็ตาม

ถ้าเขียนจำลองให้เห็นภาพ โค้ดที่สร้างขึ้นมาจะทำงานประมาณนี้:

```ts title="Route-specific handler, simplified"
function tailoredHandler(request) {
    const context = {
        request,
        params: parseParams(request.url)
    }

    return routeHandler(context)
}
```

โค้ดด้านบนเป็นเพียงตัวอย่างเพื่อให้เข้าใจคอนเซ็ปต์ได้ง่ายขึ้น ไม่ใช่โค้ดจริงๆ ที่ Elysia สร้าง หรือฟังก์ชันตัวช่วยที่ export ออกมานะ ทีนี้ลองมาเทียบกับ handler ส่วนกลางแบบทั่วไปที่ต้องเตรียมข้อมูลทุกฟิลด์เอาไว้ล่วงหน้ากัน:

```ts title="Eager central handler, simplified"
async function centralHandler(request) {
    const context = {
        request,
        params: parseParams(request.url),
        body: await parseBody(request),
        query: parseQuery(request.url),
        headers: parseHeaders(request.headers)
    }

    return routeHandler(context)
}
```

| ข้อมูลขาเข้า | Route ที่ใช้แค่ parameter | ตัวอย่างแบบเตรียมทุกอย่างล่วงหน้า (Eager) |
| --- | --- | --- |
| Path parameters | อ่าน | อ่าน |
| Body | ข้าม (เว้นแต่จะมีเงื่อนไขอื่นของ route ต้องใช้) | อ่าน |
| Query | ข้าม (เว้นแต่ต้องใช้) | อ่าน |
| Headers object | ข้าม (เว้นแต่ต้องใช้) | อ่าน |

จะเห็นว่าวิธีนี้ช่วยตัดขั้นตอนที่ไม่จำเป็นในแต่ละ request ออกไปได้เยอะมาก ซึ่งจริงๆ เฟรมเวิร์กอื่นก็อาจจะ parse ข้อมูลแบบ lazy ได้เหมือนกัน ภาพจำลองนี้แค่อยากอธิบายไอเดียการ optimize ให้เห็นภาพชัดๆ ไม่ได้แปลว่าเฟรมเวิร์กอื่นทุกตัวจะต้องกวาด parse ทุกอย่างตลอดเวลาเสมอไป

### ทำไมถึงไม่ใช้ acorn, esprima หรือเครื่องมือวิเคราะห์โค้ดทั่วๆ ไป?

เพราะ parser ทั่วไปถูกออกแบบมาให้เข้าใจไวยากรณ์ JavaScript แบบครอบจักรวาล ซึ่งเกินความจำเป็นที่เราต้องการใช้ไปเยอะมาก แถมยังต้องเสียเวลาสร้าง AST ขึ้นมาทั้งก้อน ทำให้เปลืองทั้งซีพียูและหน่วยความจำ (allocations)

Elysia เลยเลือกโฟกัสเฉพาะรูปแบบซอร์สโค้ดของฟังก์ชันที่เกี่ยวกับการใช้งาน context เท่านั้น โดยมองส่วนย่อยนี้เป็นเหมือนภาษาเล็กๆ ของตัวเอง และถ้าเจอกรณีที่ดูไม่ออกชัดเจนว่ามีการเรียกใช้ค่าไหน ก็จะเลือกวิเคราะห์แบบปลอดภัยไว้ก่อน (conservative analysis) สิ่งที่ต้องแลกกันคือขอบเขตการวิเคราะห์ที่แคบลง แต่ช่วยให้ขั้นตอนการ parse เบาลงมาก ซึ่งแน่นอนว่าวิธีนี้ไม่ได้สร้างมาเพื่อใช้แทน JavaScript parser ทั่วไปอยู่แล้ว

## เทคนิคการ optimize ของ compiler

ตัว compiler สามารถจัดลำดับการทำงาน (control flow) ให้ตรงกับสิ่งที่ route นั้นต้องการจริงๆ ทั้งการปรับวิธีจัดการ response ให้พอดีกับสิ่งที่ส่งกลับมา และเลือกดึง property แบบตรงๆ เท่าที่ทำได้ นอกจากนี้ ค่าคงที่และ schema ที่เรารู้ล่วงหน้า ยังช่วยบอกข้อมูลสำคัญที่ handler กลางทั่วไปไม่มีทางรู้ การประหยัดขั้นตอนเล็กๆ น้อยๆ หลายจุดนี้พอมารวมกันแล้วเลยช่วยเพิ่มประสิทธิภาพได้ชัดเจน ซึ่งจะเห็นผลมากน้อยแค่ไหนก็ขึ้นอยู่กับลักษณะของ route นั้นๆ ด้วย

### ตัวอย่าง: `mapResponse`, `mapCompactResponse`

Elysia มีตัวแปลง response (response mapper) เตรียมไว้หลายแบบตามความจำเป็นของ metadata ที่ต้องใช้ โดยถ้า handler ไม่ได้แตะ `set` หรือไม่ได้ระบุ status เอง ตัวแปลงแบบกระชับ (compact mapper) ก็สามารถส่งค่านั้นกลับไปได้ทันที โดยไม่ต้องเสียเวลาเตรียมพวก status หรือ header ไว้รอเลย แต่ถ้าเมื่อไหร่ที่จำเป็นต้องใช้ข้อมูลพวกนี้ ตัวแปลงแบบเต็ม (full mapper) ก็จะเข้ามารับหน้าที่ต่อเอง

การสร้างและแปลง response ที่ต้องใส่ custom header มีขั้นตอนต่างจากการส่งคืนค่าธรรมดาอยู่พอสมควร การ optimize ตรงนี้จึงช่วยเลือกเส้นทางที่เหมาะที่สุดสำหรับ route นั้นๆ แทนที่จะต้องยอมจ่ายต้นทุนแบบจัดเต็มเหมือนกันหมดทุกครั้ง

## การปรับแต่งเฉพาะสำหรับแต่ละแพลตฟอร์ม (Platform-specific optimization)

เดิมที Elysia เกิดมาเพื่อ Bun แต่ก็ยังรองรับทั้ง [Node.js](/integrations/node/), [Deno](/integrations/deno/) รวมถึงสภาพแวดล้อมอื่นๆ ผ่าน integration เฉพาะของแต่ละ runtime แต่การทำให้รันข้ามแพลตฟอร์มได้ กับการดึงพลังจาก native API ของแพลตฟอร์มนั้นออกมาใช้ เป็นคนละเรื่องกันเลย เช่น การใช้ระบบ routing ของ Bun เอง หรือเส้นทางลัดสำหรับ static response จะช่วยลดขั้นตอนการทำงานฝั่ง JavaScript ลงไปได้พอสมควร

ตัวอย่างอื่นๆ ก็เช่น:

- การจัดการ WebSocket แบบ native บน Bun ผ่าน [ปลั๊กอิน WebSocket](/patterns/websocket/) ของ Elysia
- ตัวช่วย `file()` ที่สลับไปใช้ระบบจัดการไฟล์ของแต่ละแพลตฟอร์มทันทีเมื่อทำได้
- การจัดการ header แบบ native ใน runtime ที่มีฟังก์ชันรองรับ

Elysia เคยติดอันดับในผลทดสอบ [plaintext benchmark ของ TechEmpower รอบที่ 23](https://www.techempower.com/benchmarks/#section=data-r23&hw=ph&test=plaintext) แต่นั่นเป็นผลในอดีตภายใต้การตั้งค่าแบบเฉพาะเจาะจง ไม่ใช่ผลทดสอบของตัวอย่าง v2 ในหน้านี้ เวลาใช้งานจริง แนะนำให้ลองทดสอบกับ workload และ runtime ของตัวเองเสมอ เพราะเรื่องการต่อฐานข้อมูล, การแปลงข้อมูล (serialization), middleware ไปจนถึงสภาพเน็ตเวิร์ก มักจะส่งผลต่อความเร็วโดยรวมมากกว่าการวัดผลระบบ routing เปล่าๆ อยู่แล้ว

## ต้นทุนของ JIT compiler

แน่นอนว่าการสร้าง handler เฉพาะทางแบบนี้ มีทั้งข้อดีและสิ่งที่ต้องแลกมาเหมือนกัน

### ต้นทุนใน request แรก

ตอนที่ route ถูกเรียกใช้ครั้งแรก อาจต้องเสียเวลาไปกับการวิเคราะห์โค้ดและสร้างฟังก์ชันขึ้นมาก่อน แต่พอผ่านครั้งแรกไปแล้ว request ถัดๆ ไปก็จะหยิบผลลัพธ์เดิมมาใช้ซ้ำได้ทันที ถ้าอยากรู้ว่าเครื่องของเราใช้เวลาแค่ไหน สามารถลองรันโค้ดวัดผลดูได้เลย:

```ts title="Measure eager route compilation"
import { Elysia } from 'elysia'

const iterations = 10_000
const start = performance.now()

for (let index = 0; index < iterations; index++) {
    new Elysia()
        .post('/id/:id', ({ params }) => params.id)
        .compile()
}

const elapsed = performance.now() - start
console.log(`${elapsed.toFixed(1)} ms total`)
console.log(`${(elapsed / iterations).toFixed(4)} ms per instance`)
```

ตัวเลขที่เห็นนี้รวมทั้งเวลาสร้าง instance, การลงทะเบียน route ไปจนถึงการคอมไพล์เลย ซึ่งจะมีทั้งเรื่องช่วง warmup, garbage collection, ความซับซ้อนของ route รวมถึงสเปกเครื่องที่มีผลต่อตัวเลขด้วย

ถ้าอยากยกขั้นตอนการคอมไพล์ไปทำตั้งแต่ก่อนเริ่มเปิดรับ request ก็สามารถใส่ `precompile: true` ที่ root application หรือจะสั่ง `.compile()` เองตรงๆ ก็ได้เหมือนกัน:

```ts
import { Elysia } from 'elysia'

new Elysia({ precompile: true })
    .get('/hello/:name', ({ params }) => 'Hello ' + params.name)
    .listen(3000)
```

วิธีนี้คือการยอมใช้เวลาตอนเริ่มรันระบบเพิ่มขึ้นอีกนิด เพื่อให้ request แรกไม่ต้องรับภาระหนักและทำงานได้ทันที

### การใช้หน่วยความจำ (Memory usage)

โค้ดที่สร้างขึ้นมาและ metadata ต่างๆ ย่อมต้องใช้พื้นที่ในหน่วยความจำ ยิ่งมี route เยอะ ก็แปลว่ามี handler และตัว validator ที่ถูกคอมไพล์เก็บไว้มากขึ้นตามไปด้วย ถ้าหน่วยความจำเป็นเรื่องสำคัญในระบบของคุณ แนะนำให้ลองทดสอบด้วยชุด route ที่ใกล้เคียงกับการใช้งานจริงดูนะ

### ขนาด bundle ที่ใหญ่ขึ้น

ทั้งตัว compiler และโค้ดส่วนวิเคราะห์ย่อมทำให้ขนาดแพ็กเกจของ Elysia ใหญ่ขึ้นตามไปด้วย ถึงแม้เครื่องมือ build แบบ ahead-of-time จะช่วยตัดส่วนที่ไม่จำเป็นตอน runtime ออกไปได้ แต่การได้ bundle ที่เล็กลงกับการได้ handler ที่ทำงานเร็วขึ้นก็เป็นคนละโจทย์กัน ไม่ได้แปลว่าจะมาพร้อมกันเสมอไป

### ความซับซ้อนในการดูแลรักษา (Maintainability)

การสร้างโค้ดอัตโนมัติแบบนี้เพิ่มความซับซ้อนให้ทีมผู้พัฒนาเฟรมเวิร์กไม่น้อย เพราะเวลาต้องดีบัก จะต้องเข้าใจทั้งฝั่งการประกาศ route และเส้นทางที่โค้ดถูกสร้างขึ้นมา การแยกส่วนสร้างโค้ดและส่วนวิเคราะห์ให้ทำงานเฉพาะทางช่วยให้ประสิทธิภาพตอนรันดีขึ้นจริง แต่ก็หมายความว่าโค้ดส่วนนั้นต้องมีชุดทดสอบของตัวเองอย่างรัดกุมด้วยเหมือนกัน

### ข้อควรระวังด้านความปลอดภัย (Security considerations)

`new Function(...)` ทำหน้าที่คอมไพล์โค้ด JavaScript เท่านั้น ไม่ใช่ sandbox ที่ช่วยกั้นความปลอดภัยอะไรให้ Elysia สร้างโค้ดขึ้นมาจากโครงสร้างที่ compiler ควบคุมเองร่วมกับ route ของแอป ไม่ได้มีจุดประสงค์จะเอาข้อความจาก request มารันเป็น JavaScript อยู่แล้ว แต่ถึงอย่างนั้นเราก็ยังต้องระวังเวลาจัดการกับ schema, การตั้งค่าปลั๊กอิน หรืออินพุตอะไรก็ตามที่อาจส่งผลต่อโค้ดที่ถูกสร้างขึ้น

อย่ารับโค้ดของแอปหรือคอนฟิก schema ที่รันได้มาจากแหล่งที่ไม่น่าเชื่อถือ แล้วเข้าใจไปเองว่าการคอมไพล์ route จะช่วยให้ปลอดภัยได้ นอกจากนี้ ข้อจำกัดของแต่ละ runtime เรื่องการสร้างโค้ดแบบไดนามิกก็ยังคงมีผลอยู่เสมอ ไม่ว่าโค้ดของแอปจะเขียนมาถูกต้องหรือไม่ก็ตาม

## ไลบรารีอื่นๆ ที่ใช้การสร้างโค้ดแบบไดนามิก

Elysia ไม่ใช่เจ้าเดียวที่ใช้วิธีสร้างฟังก์ชันเฉพาะทางขึ้นมาใช้งาน ตัวอย่างเช่น [Ajv](https://ajv.js.org/guide/managing-schemas.html) กับ [TypeBox](https://github.com/sinclairzx81/typebox) ต่างก็ใช้เทคนิคคอมไพล์เพื่อทำ validation เหมือนกัน ไอเดียหลักๆ คือการยอมเตรียมการให้เสร็จตั้งแต่แรก แล้วค่อยนำฟังก์ชันนั้นกลับมาวนใช้ซ้ำในส่วนที่ถูกเรียกบ่อยๆ (hot path) ซึ่ง Elysia ก็นำแนวคิดนี้มาใช้ทั้งกับการจัดการ request และการตรวจสอบข้อมูล ส่วนรายละเอียดการทำงานจริงๆ จะขึ้นอยู่กับเวอร์ชันและตัว validator ที่เลือกใช้

## การปิดใช้งาน (Opting out)

:::note[Elysia v2]

ใน v1 ตัวเลือก `new Elysia({ aot: false })` จะสลับไปใช้ handler แบบไดนามิกรุ่นเก่า แต่ใน constructor ของ v2 จะไม่มีตัวเลือกนี้แล้ว ส่วนการใส่ `precompile: true` ก็เป็นเพียงการเปลี่ยนเวลาที่จะคอมไพล์เท่านั้น ไม่ได้เป็นการปิดระบบสร้างโค้ดแต่อย่างใด

:::

สำหรับ v2 เรามีปลั๊กอินสำหรับ ahead-of-time build เตรียมไว้ให้ เช่น `elysia/plugin/aot/bun`, `elysia/plugin/aot/esbuild` และ `elysia/plugin/aot/vite` ซึ่งจะช่วยเตรียม handler ให้เสร็จตั้งแต่ขั้นตอนการ build ไปเลย แทนที่จะต้องมาสลับโหมดตอนรัน

ถ้าต้องนำไป deploy บนสภาพแวดล้อมที่จำกัดการสร้างโค้ดแบบไดนามิก แนะนำให้ลองเช็ก [ข้อกำหนดในการนำขึ้นระบบจริง (deployment)](/patterns/deploy/) ของแพลตฟอร์มนั้นๆ และรูปแบบที่ปลั๊กอินของเรารองรับ อย่าเพิ่งเข้าใจไปเองว่าแค่เปลี่ยนแฟล็ก `aot` แบบเดิมแล้วแอปพลิเคชันจะใช้งานได้

## บทส่งท้าย

ตัว compiler ยอมแลกเวลาเริ่มต้นระบบ หน่วยความจำ และความซับซ้อนในการพัฒนา เพื่อช่วยลดภาระงานซ้ำซ้อนในทุกๆ request ซึ่งข้อแลกเปลี่ยนนี้ถือเป็นหัวใจหลักในการออกแบบของ Elysia

ทางโปรเจกต์เคยเผยแพร่ [งานวิจัยความยาว 6 หน้าบน ACM Digital Library](https://dl.acm.org/doi/10.1145/3605098.3636068) เล่าถึง JIT compiler ยุคแรกและการปรับแต่งประสิทธิภาพเอาไว้ ซึ่งช่วยให้เห็นที่มาที่ไปของแนวคิดนี้ได้ดี แม้ว่าโค้ดเวอร์ชันปัจจุบันจะพัฒนาต่อยอดไปไกลกว่านั้นแล้วก็ตาม

ไลบรารีและ binding แบบ native อย่างพวก uWebSockets เองก็มีมุมมองในการแลกเปลี่ยนข้อดีข้อเสียที่ต่างออกไป และอาจทำความเร็วแซงหน้าเฟรมเวิร์กฝั่ง JavaScript ได้ในงานบางประเภท ดังนั้นควรใช้ผล benchmark เพื่อตอบโจทย์งานเฉพาะทางของคุณ มากกว่าจะมองหาผู้ชนะในทุกสถานการณ์
